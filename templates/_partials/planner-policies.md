# Planner: タスク採番・割り当て・付与基準ポリシー

本ファイルは `planner` / `team-planner` が起動直後に `Read` する。**この内容は agent .md 側に絶対に inline でコピーしない**。

## 採番規則 `task-x_y_z`

- `x`: 大項目（機能領域）
- `y`: 中項目（サブ機能 / フェーズ）
- `z`: 小項目（具体ファイル / 単位）
- 例: `task-1_2_3` = 大項目 1 / 中項目 2 / 小項目 3

## `max_retries` 判定ヒューリスティック

| max_retries | 該当例                                                                             |
| ----------- | ---------------------------------------------------------------------------------- |
| 2           | 単一ファイル変更 / 既存パターン踏襲 / 軽微なリファクタ・バグ修正                   |
| 3           | 複数モジュール横断 / 新規モジュール新設 / DB スキーマ・認可ポリシー変更 / 認証認可 |

## `executor` / `reviewer` 割り当て規則

各タスクのフロントマターに `executor` と `reviewer` を必ず指定する。plan.md のタスク一覧にも同じ値を記載する。上記の正式値以外（旧方式を含む廃止済み値）は不正値であり、使用してはならない。

| フィールド | 値          | 割り当て基準                                                                                                                                                                                            |
| ---------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `executor` | `generator` | **全タスク固定**。文書作成 / 計画ファイル更新 / チェックリスト更新 / 単一ファイル修正 / 複数モジュール横断 / 新規 API / DB・認可ポリシー / 認証認可 / UI 状態管理 等すべての実装を Generator が担当する |
| `reviewer` | `codex`     | コード変更を伴うタスク。Evaluator 前に `mcp__codex__codex` tool がレビューする                                                                                                                          |
| `reviewer` | `none`      | 文書のみのタスク / チェックリスト更新のみのタスク / 設定のみの変更タスク（コード変更を含まない場合）                                                                                                    |

コード変更を伴うタスクには必ず `reviewer: codex` を付与する。文書のみ／設定のみ／チェックリスト更新のみのタスクは `reviewer: none` とする。Codex MCP tool は計画レビュー（ステップ 3.5）とコードレビュー（ステップ 5.3.2、Evaluator 先行ゲートで APPROVED 時のみ起動）の 2 用途のみで利用し、実装には用いない（bwrap sandbox 制約により Codex 経由のコード変更は反映に失敗するため、executor として codex を割り当てる方式は廃止された）。最終検収は必ず既存 Evaluator が行う。

複雑なタスク（複数モジュール横断 / 新規 API / DB・認可ポリシー変更等）は粒度を細分化し、`max_retries: 3` と `required_advisors` の必須付与で制御する。`required_advisors` を 4 件以上並べる必要があるなら粒度過大の兆候であり、advisor 単位でタスクを分割することを優先検討する。

## `required_advisors` 付与基準

各タスクのフロントマター・plan.json に必須キー `required_advisors` を付与する基準を以下の表に従って機械的に判定する。各 advisor の **強制トリガー** に該当する場合のみ列挙し、該当しない場合は空配列 `[]` とする。「念のため付与」「曖昧なので付与」は禁止（Generator の advisor 呼出ループが膨張するのを防ぐため）。

| advisor     | 必ず付与（強制トリガー、いずれか 1 つ該当でも付与）                                                                                                                                                                                                                                                                                                                                                                                               | 付与不要（明示）                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `security`  | (a) DB スキーマ / 認可ポリシー定義の変更<br>(b) コード変更が `auth` / `session` / `cookie` / `jwt` / `token` / `password` / `permission` / 認可ロジックのいずれかに**実体として**触れる<br>(c) ユーザー入力を SQL / system call / file path / URL に渡す経路の追加・変更<br>(d) 環境変数・シークレット・API キーの取り扱いを変更<br>(e) 認可ロジック（role 判定・ownership 判定）の追加・変更                                                     | 表示テキスト変更のみ・ハードコード文字列・docs・既存の認可ポリシー説明文修正のみ |
| `architect` | (a) モジュール・パッケージ配下に**新規ディレクトリ**を追加<br>(b) 各モジュール・パッケージの公開エントリポイント / 依存定義（`exports` / `main` / `dependencies` 等）を変更<br>(c) DB スキーマ / マイグレーション / インデックス / 認可ポリシーの新規定義（テーブル新設・カラム追加・型変更）<br>(d) ファイル移動（`git mv` 相当）を伴うモジュール責務の再配置<br>(e) アプリケーションの route 構造変更（新規セグメント追加・レイアウト階層変更） | 既存モジュール内の単一ファイル編集・テストのみ・docs                             |
| `ui-ux`     | (a) 画面・ページの **新規追加**<br>(b) Dialog / Modal / Drawer / Sheet 等の新規コンポーネント追加<br>(c) ナビゲーション要素（Header / Sidebar / Tab）の項目追加・順序変更<br>(d) フォーム input / select / button の **新規追加**（既存スタイル変更ではない）<br>(e) アクセシビリティ要件（aria-\* / role / focus 管理）の追加・変更                                                                                                              | typo 修正・既存コンポーネントのスタイル微調整・文言変更・docs                    |
| `tech-lead` | (a) 3 ファイル超を横断する状態管理（共有 state / store / クエリキャッシュ等）の追加・変更<br>(b) メモ化 / 遅延境界（性能最適化のための境界）の **新規導入**（性能要因が明示される場合）<br>(c) Realtime 同期 / WebSocket / Server-Sent Events 経路の追加・変更<br>(d) E2E / 結合テスト戦略の追加（テスト・E2E 設定変更含む）<br>(e) ビルド設定 / 型チェック設定 / モノレポ構成ファイルのビルド・型構成変更                                        | 単純な UI コンポーネント追加・既存パターン踏襲のロジック・docs                   |

## `required_advisors` 判定アルゴリズム

各タスクについて以下を順に実行する:

1. 上記 4 表のトリガー (a)〜(e) を **タスクの予定変更内容** と機械的に突合する
2. 該当する具体根拠（ファイルパス例・キーワード例・操作内容）を `plan.md` のタスク一覧の `required_advisors` 列の隣に短く併記する（後から検証可能にする）
3. 1 つも該当しない場合のみ `[]`（空配列）。**「念のため付与」「曖昧なので付与」は禁止**
4. 複数該当時は全員列挙、配列順は `security → architect → ui-ux → tech-lead`

## 並列実行に適した depends_on を張る観点

> iterate-team Planner が従う。

iterate-team は `plan.json` の `depends_on` をトポロジカルレベル化（`<plugin_root>/scripts/team-compute-waves.sh`）して同 level を 1 wave として並列実行する。Planner は wave 内のタスクが互いに **物理的に競合しない** よう depends_on を設計する責務を負う:

| 観点                             | 望ましい設計                                                                                     | 避けるべき設計                                                   |
| -------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| **同一ファイル編集**             | 同じファイルを編集する複数タスクは **直列化**（depends_on で順序付け）                           | 同じファイルを並列タスクで編集 → wave merge で必ずコンフリクト   |
| **既存ファイル追記 vs 新規作成** | 新規ファイル作成タスクは並列化を推奨                                                             | 既存ファイルへの追記タスクが複数並ぶと merge conflict のリスク高 |
| **過剰依存**                     | 物理的に独立なら `depends_on: []` で並列化                                                       | 「念のため」順序付けて wave 数を増やすと並列化のメリット消失     |
| **論理依存の明示**               | 後段タスクが前段の出力（API シグネチャ・型定義・スキーマ）に依存する場合は必ず depends_on を張る | 暗黙の論理依存を放置すると並列実装でビルドエラー / 型不整合      |

判定手順:

1. 各タスクペア (A, B) について「同一ファイルを編集するか」を **タスクの予定変更ファイル一覧** から機械判定する。同一ファイルがあれば **片方を他方の depends_on に追加**（順序は任意だが宣言順を優先）
2. 後段タスクが前段タスクの出力（新設関数・型・テーブルカラム）を参照するなら depends_on を張る
3. それ以外は `depends_on: []` で並列可とする
4. **wave 数を `task_count / 4` 程度に抑える**（並列度 4 のため、wave 数が task 数に近づくと並列化メリットが消える）

Codex 計画レビュー（ステップ 3.5）の観点 23（並列実行を前提とした depends_on の漏れ）に該当するため、本判定基準は機械的に追跡可能な根拠（ファイルパス）を `plan.md` に併記すること。

## 修正フロー時の挙動

修正フローには **2 経路** があり、Planner 側の処理は同じ「上書き Write」に集約される:

- **経路 A: ユーザ修正点指示**（ステップ 4 で「修正」が選択されたとき）。Orchestrator から「修正点 + 既存 plan-summary.md / plan.json のパス」が渡される
- **経路 B: Codex 計画レビュー応答**（ステップ 3.5 で `## status: REQUEST_CHANGES` が返ったとき）。Orchestrator から「`<summary_path>` + `responses/codex-plan-review-rev-<N>.md` のパス + `codex_plan_review_round` 値」が渡される（入力節「形式 6」参照）

いずれの経路でも、既存の `plan.md` / `plan-summary.md` / `plan.json` / `task-x_y_z.md` を **上書き Write** で更新する。`required_advisors` の値も上記判定アルゴリズムに従って再評価し、初稿で付与漏れがあれば修正版で補完する（過剰付与は削除する）。Orchestrator 側はこの再 Write のあとにステップ 3.2 パターン B から再走行（validate-plan + Planner 出力コミット `plan_revision +=1`）を行い、ステップ 3.5（Codex 計画レビュー）に再入する。

> `plan_review_round` カウンタの初期化タイミング（ステップ 3.5 入口でリセット・自動修正ループ内では引き継ぎ）の詳細規則は [`<plugin_root>/commands/iterate-team.md` ステップ 3.5（Single Source of Truth）](<plugin_root>/commands/iterate-team.md) および [`<plugin_root>/operations/iterate-team-runbook.md`](<plugin_root>/operations/iterate-team-runbook.md) を参照。

## 細分化原則

タスクは `max_retries` の範囲（2〜3 試行）で完了する粒度に分割する。1 タスクで 5〜15 試行が必要な大物は複数タスクに分割すること。`required_advisors` を **4 件以上並べる必要があるなら粒度過大の兆候** であり、advisor 単位でタスクを分割することを優先検討する。

## テスト可能な受け入れ条件（iterate-team TDD 前提）

iterate-team では `reviewer: codex` のタスクで `team-test-coder` が実装前に受け入れ条件からテストを先行作成する（テストファースト、`tdd-policy.md`）。そのため各タスクの受け入れ条件（EARS）は **観測可能な入出力・状態で記述**し、test-coder がテスト化できる粒度にすること（「正しく動く」のような検証不能な表現を避ける）。Planner への新フィールド追加は不要（TDD ゲートは `reviewer` フィールドから Orchestrator が機械判定する）。

## RALPLAN-DR 観点（計画の必須検討項目）

すべての plan.md 生成時に以下の 5 観点を検討し、**想定リスク**・**スコープ**・**完了条件**の各章に反映すること:

| 観点                                         | 内容                                                                          |
| -------------------------------------------- | ----------------------------------------------------------------------------- |
| **原則（Principles）**                       | 変えてはならない設計・規約上の制約（例: 認可ポリシー必須、EARS 形式、型安全） |
| **決定ドライバー（Decision Drivers）**       | 選択肢を絞り込む主要因（パフォーマンス / 保守性 / 開発速度 / リスク低減）     |
| **選択肢（Alternatives）**                   | 同じ目的を達成する代替アプローチと採否の根拠                                  |
| **リスク許容度（Risk Tolerance）**           | 許容できる失敗の範囲と回復戦略（リトライ上限・ロールバック計画）              |
| **タイムライン制約（Timeline Constraints）** | depends_on チェーンによるクリティカルパスと優先順位                           |
